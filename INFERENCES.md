## Still guessed or not read
- **Panel positions** of the numbers and icons come from the decompiled arithmetic in `seg2_0D58` (window-relative; I took the window origin as 0,0, which is right for window coordinates) and the order of the icons (PICT 1101..1107) from the order of the `seg2_0CB4` calls: not evaluated by running the original.
- **Palette handling over time**: the game switches tables (`clut` 999 is set first, then 128; 129 and the three flash variants derived by `seg2_1974` are loaded); the port uses 128 throughout and does not fade or flash. Which colour table the backdrop patterns bring (they are remapped to table 128 like pictures) is not verified against the real game.
- **Colour remapping**: the Mac remapped each picture's own colours to the nearest entry of the game table (with its own inverse-table rules); the port uses plain nearest-RGB, so a few colours may differ slightly.
- **Mouse speed** 1:1 (the ADB driver's scaling is unread); **Ticks** 60.15 Hz virtual; `loop_hz` 60 by default (a setting); audio device 22050 Hz (the original: 22254.5 Hz); mixer gain per volume step 0/40/70/100 %.
- Not read at all: the title screen, menus and dialogs (CODE 2, 4, 8), music, fades.

## Input between rounds, scale (reported by the user's playtest)
- The mouse button and movement are now tracked in one place, so a button released during the end-of-round sequence is no longer remembered as held; a new game or round starts from the real button state. Movement during the end-of-round loops is passed to the shooter (the loops never fire). That the original lets the shooter move there is read from the code: the ADB mouse driver adds to the pending movement at all times, and the end-of-round loops (seg3_26C2, seg3_2836) run the move pass, which calls the shooter's move callback (seg3_5216); the fire routine (seg3_2256) is not called from them.
- A coin that "stays at the top with reversed gravity" matches the ported `move_yummy` (seg3_454C, checked against the 68k): gravity is added only when the sideways speed is non-zero, and a burst coin can get sideways speed 0 (`rnd(0x46)` = 0) while flying upward, so it rises, is clamped at the top and never falls. Probably an original bug; not seen live.
- `scale` in `apeiron.ini` accepts hundredths (0.5 to 4).

## Icon and shooter speed
- Application icon: `icl8` 128 with the mask from `ICN#` 128 (the 8-bit icon uses the Mac's standard colour table, rebuilt in `cicn.c`; the result looked right: green caterpillar, yellow teeth). Set as the SDL window icon; embedded in apeiron.exe by build_windows.ps1 when the data files are at hand.
- Shooter speed cap: read from `seg3_5216` (checked against the 68k): each step the shooter moves by half of the pending mouse movement, at most 13 px per axis; the rest stays pending. So a long swipe speeds up (the pending amount is large) and then holds at 13 px per step until the pending movement runs out.

## Game time and slowdowns (measured 20 s runs, auto-fire, 60 Hz loop)
- The game counts a Tick only when the Ticks value it sees has changed since the last pass (`game_pass`, `seg3_1666`), and adds one more in each game step (`step_update`), so the game's own tick counter runs at about 148 % of real Ticks. A pass that sees two new Ticks still counts one. On the original the loop ran faster than the Ticks, so none were missed; at a 60 Hz loop against 60.15 Ticks per second a few are, so game time ran 142 to 149 % in 5 s windows (about 2 % slow on average) with `steady_ticks = 0`, and a steady 149.7 % with `steady_ticks = 1`. This is the one slowdown cause found so far; it is small and needs no stall. It was not changed here, since fixing it would make the game faster than it was.
- The game's own work is about 0.025 ms per pass; the wait for the monitor is about 14.7 ms of each 16.7 ms frame; no late frames in these runs. Stalls on the user's machine have not been seen here: `hitch_log` is there to catch them.

## Intro colours, end-of-round speed, coins (after the user's playtest)
- Intro logo (PICT 889): the screen palette is colour table `clut` 889, not the picture's own colour table (the pack's picture lists the same colours in another order). All 150 colours the picture uses match an entry of clut 889 exactly, so each pixel is moved to that entry and entries 1..246 are rotated as before (entry 247, the yellow "Star Wars" text, is outside the turned range and stays). The first version used the picture's own table and turned the text too; the user's four screenshots show the smooth red / blue / violet drift with fixed yellow text, which the new version reproduces (checked by pictures of the first step and the 41st).
- `steady_ticks = 1` made the end-of-round loops (mushroom repair, bonus count) crawl when drawing a frame took longer than a step: each call to the wait routine was one pass. It now counts the passes that fell due meanwhile (up to 8), as the main loop does. Checked with drawing slowed to 50 ms: Ticks still ran at about 60 per second there. Not seen on the user's machine.
- The coin that stays at the top: the user's mother remembers the original doing it too, which confirms the ported behaviour as original.
- A scores file from 2001 loaded correctly, which also shows the QEMU image ran 1.0.2 (user's report).

## Original bugs behind .ini switches
- **fix_coin** (off = as the original). A burst coin gets a random sideways speed `rnd(0x46) << 12` with a random sign; when the draw is 0 the coin has no sideways speed, and `move_yummy` (seg3_454C) adds gravity only while the sideways speed is non-zero, so a coin flying up never turns, is held at the top (`POS_V` clamped to 0) and never leaves. Measured: 26 of 1746 upward coins (1.5 %) in 3000 bursts. The fix gives such a coin a sideways speed of 1/16 px per step; it takes no extra random draw, so everything else stays as it was (the same 1746 coins came out). The original's stuck coin was confirmed by the user's mother. Checked headless only.
- **The centipede "glide"** (several heads together, falling to the bottom in seconds at a side wall, in later waves where the wave starts as many single heads): NOT reproduced and NOT fixed (superseded: found in a recording, see "Wall glide" at the end). A watcher for "a head comes down 5 rows within 40 passes without poison" found nothing in about 6 million simulated passes of the game's own set-up for waves 10 (many heads, a swaying auto-firing shooter), nor in 600 set-ups with two to four heads at a side wall with random directions. Head-on collisions (two heads turning down together, `move_pede` / `turn`) are common but never repeated quickly in these runs. `pede_log = 1` writes `apeiron_pede.txt` when the user sees it: the last 40 passes of that head and its nearest head.

- **Wall glide (`fix_glide`)**: from a Wave 28 recording (`apeiron_replay_20261030_134326.bin`, steps 34031 to 34222): a head moving right reaches x=416 (the wall) just as a head moving left starts from the wall; the collision code puts the left-mover at `other.x + width` capped at the wall (416), which is the other head's own place, then swaps their directions. At the end of every row they meet again and stay on top of each other, sliding down the wall (y 240 to 464) and back up. The original 68k code does the same from the same state (`test_replay`: 0 differences from step 33,701 to 36,312, the 68k copy having been reset to the port's state at 33,700, a round start). `fix_glide = 1`: when the cap would apply, the head keeps its own place. Checked only on that recording (the pair separates and the heads spread out instead of locking); with the fix on, a recording drifts from its recorded game as soon as the fix changes a collision, as expected. Mirror case at the left wall (`d6 < 0`) is changed the same way but not seen in a recording.
